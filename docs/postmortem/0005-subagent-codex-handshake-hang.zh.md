# 事故复盘（postmortem） 0005：Codex subagent 握手挂起

[English](0005-subagent-codex-handshake-hang.md) | 中文

Status: resolved（发布前缺口由同一系列更早的提交关闭；本提交以协议帧活动看门狗与终态帧诊断关闭发布后方面）

## 摘要

当被委派的 Codex app-server 保持存活却停止响应时，一次 `subagent_codex` 调用可以无限期挂起（[讨论 #6226](https://github.com/deepseek-ai/deepseek-harness/discussions/6226)）：子进程既不退出不关流，而发布前握手对这个输入没有结算路径，于是运行、它的工具调用与会话的深挖状态只能等一个外部行动者——取消、终止或服务器重启——来释放，没有失败、没有诊断、也没有重试。两个发布前握手请求现在携带每请求截止期限（`handshakeTimeoutMs`，默认 `60_000` 毫秒，`0` = 关闭）；沉默的 app-server 会在期限处以 `transport` 类别让运行失败，并在处置前记录一条存活详情。同一报告的发布后方面——子进程完成轮次并退出而运行仍在等待——由本提交的协议帧活动看门狗与终态帧诊断关闭，本事故复盘已解决。

## 概述

Codex 提供方只在两个握手请求完成之后才发布运行，对象是它刚 spawn 的 `codex app-server --stdio` 子进程：`initialize` → `initialized`，然后 `thread/start`。每个请求恰好能被四种观察到的事实结算：一个响应、请求信号的中止、协议流的结算，或子进程的直接失败。共享 JSON-RPC 传输拥有待处理项表，只在响应、中止或流结算时结算条目；它自己没有计时。

事故的输入正是这个划分的补集：一个保持存活、保持 stdio 流打开、且从不回答的子进程。没有响应到来，中止只有用户行动时才会触发，流永不结算，子进程也从不失败，于是这个待处理请求——以及建立在其上的运行——无限期等待。后台 Job 没有人去中止，而运行内部也没有任何东西能把沉默转化为失败。

同一报告还描述了发布后的方面：子进程完成了它的轮次并退出，而 dsh 侧的运行仍在挂起。当 `turn/completed` 通知的轮次 id 与活动轮次不匹配时，wire 会把它静默丢弃，而且发布后的竞争本身没有任何活动边界；这两个事实都由本提交的活动看门狗与终态帧诊断关闭。

## 影响

间歇性的 `subagent_codex` 调用永不返回。在前台，工具调用与会话的深挖状态无限期等待，报告者观察到点击取消没有效果；在后台，one-shot Job 停留在飞行中，没有完成通知、没有失败诊断、也没有重试。只有杀掉或重启 dsh 服务器才释放挂起。没有数据损坏，也没有安全影响：卡住的运行只持有它自己的工作区，而挂起前写入的文件副作用是子进程完成的真实工作。

## 根因

发布前的结算路径对失败空间做了不完整的划分：响应、中止、流结算与子进程失败，唯独没有一条路径对应「存活、开着、沉默」的子进程。传输的待处理项设计对协议对端是正确的——它只在观察到事件时结算——但 app-server 是一个子进程，而发往外部子进程的请求需要一个由调用方策略拥有的时间边界。取消是用户决定，子进程死亡是产品事实，两者都不是截止时间：无人值守的后台运行两者都没有。

测试矩阵镜像了同样的不完整。模拟实现演练了取消、子进程退出、无效帧与流关闭，但从没有演练过一个在预期响应时刻之后仍保持存活且沉默的子进程——这正是区分卡住的握手与健康握手的唯一输入。

而且失败构造器没有任何存活观测：当发布前失败终于浮现时，其诊断无法说明 app-server 进程是否仍在运行，还是子进程已经退出而其受管 range 仍然开着——而这正是决定一次重试是否值得尝试的那个事实。

报告中观察到的「取消无效」与同一个划分一致：在当前代码树里，请求信号的中止是发布前唯一的释放路径，而每条释放路径都需要一个行动者——取消、终止、重启。修复让行动者不再必要：截止时间是运行本身可以观察到的事实。

报告的发布后方面——子进程完成轮次并退出而运行仍在等待——在报告的代码树里有它自己的两个缺口：轮次 id 与活动轮次不匹配的 `turn/completed` 通知被 wire 静默丢弃，且发布后的竞争没有自己的活动边界。两者都由本提交的协议帧活动看门狗与终态帧不匹配诊断关闭。

- 本提交用新的 `Config.handshakeTimeoutMs`（默认 `60_000`，`0` = 关闭）为两个发布前握手请求装上截止期限，把期限失败归类为 `transport`，并在安全失败诊断中记录处置前的存活详情。
- 本提交以协议帧活动看门狗与终态帧不匹配诊断关闭发布后的方面；系列以杀死子进程的运行控制继续。

## 已添加的防护措施

- [`Config.handshakeTimeoutMs`](../../packages/subagent/subagent-codex/README.zh.md) 通过传输的每请求截止期限约束两个发布前握手请求：默认 `60_000` 毫秒，`0` 关闭，验证为非负有限且不超过共享 `MAX_TIMER_DELAY_MS`。
- 撞上截止期限的握手在其所在阶段以 `transport` 类别让运行失败——传输沉默，区别于 `unknown`——因此诊断指明机制。
- [`startupLivenessDetail`](../../packages/subagent/subagent-codex/src/run.ts) 在处置前用零延迟 `waitForExit` 探测已获取的子进程，并对两种意外情形向安全失败诊断追加固定的存活详情：期限已过而 app-server 进程仍在运行，以及子进程已退出而其受管 range 尚未停稳。
- wire 规格固定两个握手方法上的每请求截止拒绝，并证明零截止不装任何东西；run 规格用确切消息固定两种存活详情，同时针对取消、spawn 失败、无效帧、关闭前 EOF 与清理竞争的既有诊断保持不变；真实产品通道证明默认截止期限下健康路径不受影响。
- [`Config.runActivityTimeoutMs`](../../packages/subagent/subagent-codex/README.zh.md) 为两个产品提供方约束发布后的协议静默——Codex app-server 帧与 Claude Code SDK 流消息：默认 `300_000` 毫秒，`0` 关闭，验证为非负有限且不超过共享 `MAX_TIMER_DELAY_MS`。
- 超过截止期限仍保持静默的发布后运行以类别 `transport` 失败，其细节指出最后观察到的帧或消息；失败阶段标明静默发生在轮次提交之前还是之后。
- Codex wire 在 `turn/completed` 引用了另一线程或轮次、或在运行提交轮次之前到达时使运行失败，并通过提供方诊断接收器上报——但不失败——无法属于本运行的非终态帧。
- 运行规格固定了触发、重置、禁用与终态不匹配路径，附带精确的诊断消息；真实产品通道保持不变并通过。
- [运行活动看门狗 Agent Note](../../.agents/notes/implemented/feature/2026-09-15-subagent-run-activity-watchdog.zh.md) 记录设计决策，[握手截止 Agent Note](../../.agents/notes/implemented/feature/2026-09-15-codex-handshake-deadline.zh.md) 记录其发布前姊妹篇，包括为什么该观测使用现有的 `waitForExit(signal?)` 而不是新的 subprocess seam 方法。

## 教训

- 发往外部子进程的请求只会被四种观察到的事实结算——响应、中止、流结算、子进程失败——调用方策略还必须覆盖时间本身；取消与死亡都不是截止时间。
- 失败诊断所需的存活事实必须在处置摧毁它之前被观测；探测只在进程仍可寻址时才便宜。
- 协议握手的测试矩阵必须包含存活但沉默的子进程——这是其他任何结算路径都产生不了的输入。
- 报告的挂起命名的是一个症状类别，而不是单一机制；修复系列逐个关闭了 Codex 运行结算划分的方面——每请求截止期限、握手截止时间、以及本提交的发布后看门狗与终态帧诊断——现在每个方面都有边界。
