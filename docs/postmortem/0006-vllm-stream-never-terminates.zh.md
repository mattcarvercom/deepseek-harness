# 事故复盘（postmortem） 0006：永不终止的 vLLM 流

[English](0006-vllm-stream-never-terminates.md) | 中文

Status: resolved

## 执行摘要

两个 LLM（大语言模型）适配器都用同一个看门狗约束流——一个按读空闲计时器，任何线路上活动都会让它重新计时。[讨论 #5007](https://github.com/deepseek-ai/deepseek-harness/discussions/5007) 报告的 vLLM 端点（服务 Qwen3.8-27B）正是这种输入：流持续发送数据却从不产生模型内容，看门狗因此被无限期地反复重置——请求既不失败也不完成，而没有失败发生，就没有任何重试，也没有任何报告。本提交为两个适配器增加第二个独立的界限——内容空闲截止（`streamContentIdleTimeoutMs`，默认十分钟，`0` 禁用），它在流建立时武装，只由真实模型输出重置——这类流现在会在有限窗口内以可重试的 `TIMEOUT` 失败。

## 概述

两条流式路径都带一个按读空闲看门狗（`streamIdleTimeoutMs`，默认五分钟，`0` 禁用），它约束单次从线路读取可以沉默多久。两个适配器都在任何流活动（而非仅内容）上重置它：DeepSeek 适配器在每条 SSE 注释——线路上的 keep-alive 行——上调用 pulse（续时），pi-ai 适配器在它 SDK 发出的每个值上重置它。该看门狗检测完全沉默的连接，并且可靠。但它的补集——一个保持活动、从不产生内容、也永不终止的流——是唯一它无法变成失败的输入：每条 keep-alive 都远远落在按读预算之内，流永不关闭，失败从未发生。以这种方式挂起的请求永远不会进入重试策略——它重试的是失败，而不是沉默——也不会产生诊断，因为没有任何东西可报告。

## 影响

[讨论 #5007](https://github.com/deepseek-ai/deepseek-harness/discussions/5007)（"[Bug] Cannot stream from vLLM end point"）报告了这一症状类别：报告者有一个"通过 vLLM 配置的 Qwen3.8 27B 端点"，并且"第一次启动 dsh 并通过 UI 配置端点后，一切如预期工作。但再次启动 dsh 时，就再也没……"。该讨论仍处于未回答状态，而报告本身就是无法完成请求的记录。报告没有说明该端点配置在哪个适配器之下；本树的两个 LLM 适配器都有这个漏洞，两条路径会以同样方式挂起——一个工具调用、一个轮次或一个后台作业无限期等待，直到外部行为者取消、杀掉或重启进程，这是[事故复盘 0005](0005-subagent-codex-handshake-hang.zh.md) 确立的对外部进程运行不可接受的同一失败特征。没有数据损坏，但被冻结的用户无法区分模型慢与端点坏，也不存在可指向的诊断。

## 根因

按读空闲看门狗的重置规则把任何活动都当作存活流，而一个坏状态是 keep-alive-only 流的端点，在该规则下构造性地不可见。两个缺口叠加。其一，不存在第二个基于内容的界限：没有任何东西度量真实输出的沉默，只度量线路的沉默，因此一个持续发送数据却没有内容的流，在所有既有界限看来都是健康的。其二，没有失败，因此没有重试：默认重试策略（重试 5 次）只对失败触发，一个永远挂起的流从未进入 harness 拥有的任何恢复路径。两个适配器的测试矩阵演练了看门狗的输入——完全沉默的流——但没有演练它的补集：一个永远活动、永远无内容的流。

## 时间线

- 按读空闲看门狗（`streamIdleTimeoutMs`，默认五分钟，`0` 禁用）存在于两个 LLM 适配器中，由任何线路活动（包括 keep-alive）重置。
- [讨论 #5007](https://github.com/deepseek-ai/deepseek-harness/discussions/5007) 报告一个通过 vLLM 服务 Qwen3.8-27B 的端点：首次通过 dsh 使用正常，之后启动 dsh 就无法流式；该讨论仍处于未回答状态。
- 对该报告的深入排查在当前代码的两个适配器中都发现了这个漏洞：唯一的流界限被 keep-alive 活动重置，因此一个保持流打开却不产生模型内容的端点会让请求永远挂起——无失败、无重试、无报告。
- 本提交在两个适配器上武装第二个界限：内容空闲截止 `streamContentIdleTimeoutMs`（默认十分钟，`0` 禁用，上限为共享的 `MAX_TIMER_DELAY_MS`），只由模型内容重置——非空文本或推理增量，或工具调用载荷。

## 新增防护栏

- `streamContentIdleTimeoutMs` 是两个适配器上的已校验配置字段——非负有限数，不大于共享的 `MAX_TIMER_DELAY_MS`，默认十分钟，`0` 禁用——记录在[配置目录](../config-catalog.zh.md)与两个包的 README 中。
- [`dsh-timeout`](../../packages/util/timeout/README.zh.md) 中的新原语 `progressDeadline`：在流建立时武装，只由显式 `progress()` 调用重置，跨越读之间的空档持续运行；`<= 0` 是无定时器直通。按读看门狗与内容截止在每个请求上融合成一个中止信号。
- 两个消费循环只在 token 级内容（`isTokenDelta`）上推进截止：keep-alive 注释与 SDK 元数据值从不延长它。
- 触发的截止抛出 `LlmError('… stream content idle timeout after <ms>ms', 'TIMEOUT')`；`TIMEOUT` 本就在默认重试策略的可重试 code 中，因此既有的五次重试策略现在有了可重试的失败。
- 适配器测试分别钉住：keep-alive-only 流在截止处失败、持续产生内容的流越过截止存活、`0` 作为禁用；pi-ai 测试额外钉住内容截止在与 SDK 对已中止流的带内转换的竞争中胜出。

## 教训

- "对端还活着"不等于"请求在推进"：按任何活动重置的界限防的是沉默，不是活动性的无进展；一个坏状态是 keep-alive 喋喋不休的端点需要的是基于进展的界限。
- 从未发生的失败永远不会被重试：重试策略消费的是失败，一个永远挂起的流停留在所有恢复路径之外；修法是让失败发生，而不是再添加一条恢复。
- 流式边界的测试矩阵必须包含其看门狗输入的补集：一个永远活动、永远无内容的流。
