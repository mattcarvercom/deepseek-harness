# Agent Note: In-Browser Read-Aloud for Assistant Responses (Vendored sanotts Runtime)

Status: proposed

[English](2026-09-18-in-browser-readaloud-sanotts.md) | 中文

## Problem

长时间挂着会话的用户——或者在嘈杂环境、手机上、低视力下阅读的用户——希望助手回复能被朗读出来。dsh web 客户端此前没有任何音频界面。

几条显而易见的路线都达不到产品要求。Web Speech API 取决于操作系统和浏览器恰好安装了什么语音：质量不一、可用性不一，输出无法跨机器钉扎或验证。服务端合成器（宿主背后的 sanotts Python 进程，或远程 TTS API）会把一个离线、自托管的产品变成有逐句网络依赖、要管理 API key、或要发布 Python 运行时的产品——而产品要求恰恰相反：没有服务器、没有 Python，合成发生在拥有扬声器的那台机器上。

缺的是把一套固定的、自托管的语音模型带进浏览器的方式：只在真正有人朗读时才加载，并且把那段代码留在所发布 bundle 的许可边界之外。

## Proposal

新增 `@deepseek-ai/dsh-client-ui-readaloud`，一个带两个条目的 web 客户端插件：`conversation.chat.assistant-actions` 操作条上每条助手消息的朗读/停止按钮，以及通用设置区中的「自动朗读回复」行（`ui-readaloud` 设置命名空间，`autoRead` 布尔值，默认关闭，由包的 Node 半部通过标准设置服务注册）。

合成引擎是引入（vendored）的 **sanotts** 运行时（npm `sanotts-web@0.3.0`），GPL 许可的 wasm 语音合成引擎，与仓库自身语音工作同一模型谱系。资产——运行时、G2P 与语音 wasm 模块、`heart` 与 `heartnano` 音色权重——被引入到 `assets/sanotts/`，带 sha256 清单，由 web 构建逐字节复制到 `dist/sanotts/`，并在首次使用时按 URL 加载：

- **首次使用，而非启动时。** 客户端 bundle 不静态导入运行时的任何东西。首次合成时，引擎对 `<document base>sanotts/index.js` 执行动态 `import()`；模块的 `assetBase` 与 `voiceBase` 都解析到同一个自托管目录。由于显式传入了 voice base，运行时在没给 base 时才会咨询的 Hugging Face CDN 回退永远不会被触碰。该功能的任何请求都不离开页面源。
- **一个引擎、一个导演、一个上下文。** 页面级引擎缓存模块导入、wasm 加载与每个音色的权重（加载失败会被移除并在下次调用重试；合成输出上限 300 秒）。页面级导演拥有一个惰性创建的共享 `AudioContext` 和至多一个进行中的播放；开始任何朗读都会先停止前一个，无论它属于哪个会话，因此音频从不重叠。播放是原生 `AudioBufferSourceNode`——刻意从不调用运行时自带的 `playAudio`，让触碰音频的那条 GPL 代码路径留在边界的合成一侧。代数令牌丢弃那些在落地之前请求已被取代的合成结果。
- **只朗读可朗读文本。** 每条消息的文本块被拼接、按 GFM 围栏规则剥离开栏代码，再交给共享的 GFM 纯文本投影。推理、工具调用、轨迹和系统文本从不被合成；围栏代码被完全跳过；图片读其替代文本；原始 HTML 原样透传。
- **自动朗读语义。** 偏好开启时，一条消息在它变得可朗读的时刻被朗读一次——定稿节点到达，即转录对行内图片所用的同一个稳定信号——会话中更新的一轮开始时会停止正在播放的内容。偏好打开时已经可读的行刻意不会被重新朗读；每会话已朗读集合把该保证维持为跨重新挂载每条消息至多一次。

## GPL 边界与资产钉扎

GPL 运行时是一个*被服务的资产*，而不是依赖：它不存在于任何 `package.json`、tsdown 打包图或 Vite 模块图中，而是以静态文件形式由 dsh 宿主提供。因此 copyleft 材料停留在产品编译代码之外；边界在加载时，且由构造强制（唯一的引用是一个 URL 字符串）而非靠审查。GPL 声明存放在 `assets/sanotts/` 内、与其许可的代码并排，语音权重携带各自的 MIT 声明，`MANIFEST.md` 记录 npm 压缩包的 sha256 与 npm sha512、音色权重来源提交，以及一个逐文件 sha256 表——`tests/asset-manifest.spec.ts` 在每次运行时把该表与目录重新对账。npm 压缩包本身随 `files` 发布，作为钉扎记录——从不被获取，从不被执行。

## 音色选择

`heart`（227 万参数，f32，约 9.1 MB 权重）是默认音色；`heartnano`（29.4 万参数，int8，约 337 KB）在同一音色注册表中作为低资源回退注册。注册表是一个键联合加一个默认常量——为日后更多音色做好了结构准备，但按产品决定本次发布没有选择器：更换默认音色是代码改动。

## 考虑过的替代方案

- **Web Speech API（`speechSynthesis`）。** 在每一个重要的维度上输掉：音色是操作系统和浏览器发货的东西，质量、可用性甚至基本覆盖都逐机器不同；输出无法钉扎、快照或测试；一些平台根本没有可用音色。
- **服务端 TTS（宿主拉起的 sanotts Python 进程，或远程 TTS API）。** 两个方向都破坏自托管/无服务器要求：Python 进程是产品不发布的运行时，API 是有 key 要管理的逐句网络依赖——正是要求排除的东西。
- **把 npm `sanotts-web` 运行时打包进客户端 bundle。** GPL 代码会因此进入产品的编译模块图——进入每个消费者的构建——而不是作为被服务的、带版本号的资产放在旁边。基于 URL 的动态导入让模块图保持无 GPL，同时资产保持钉扎且同源。
- **CDN 或 Hugging Face 托管的语音权重（运行时默认行为）。** 运行时只在没给 `voiceBase` 时才咨询 CDN；显式传入自托管目录正是让「无网络」成立的机制，依赖默认值会使钉扎失效。
- **以 `heartnano` 为默认。** 它小 27 倍，但产品决定让默认体验用保真度更高的 `heart`；`heartnano` 仍留在注册表中供需要低资源选项的调用方使用。
- **设置中的音色选择器。** 本次发布明确不在范围内；音色注册表的存在使日后增加一个变成数据改动而非重新架构。

## 验收标准

- 自动朗读关闭（默认）时，从不朗读任何东西。
- 助手消息上的朗读按钮朗读那一条消息；合成或播放期间显示停止控件；开始任何其他朗读都会停止它，跨会话也不存在两个重叠的朗读。
- 自动朗读开启时，每轮的最后一条助手消息在轮次稳定后恰好被朗读一次；新一轮开始停止上一轮播放；偏好在页面刷新后保持（环回主机上持久保存，否则在进程内存中）。
- 只朗读用户可见文本：没有推理、工具调用、轨迹或系统文本；围栏代码被跳过；markdown 被投影为纯文本。
- 每个资产请求都是对所提供的 `sanotts/` 目录的同源请求；不接触 CDN；清单哈希在每次测试运行时通过验证。
- 浏览器 bench 带着该插件启动组装好的 web 应用，在无音频的情况下断言条目、偏好与播放生命周期；单元套件覆盖引擎接缝、导演状态机、可朗读文本策略、设置存储，以及 Node 半部的注册与销毁。

## Risks

- **自动播放策略。** 在没有先前用户手势的页面上，浏览器可能让共享 AudioContext 保持挂起，因此首次自动朗读可能无声，直到下一个手势解锁它。缓解：上下文在 `speak()` 内创建，因此手动朗读出生在其点击内；该限制记录在包 README 中。
- **五分钟截断。** 运行时 300 秒的输出上限会截断更长的消息；这是作为已知限制记录的，而非隐藏的。
- **缩进代码会被朗读。** GFM 四空格缩进代码不是围栏，因此按裁剪后的源码朗读；围栏代码才是被跳过的情况。
- **GPL 相邻性。** 该 copyleft 运行时是产品代码按 URL 引用的被服务资产；加载时边界、随附的许可声明、钉扎的清单是对这种相邻性的常备回答，任何重新引入都必须在同一变更中重新记录清单。
- **资产重量。** 引入目录由 `heart`（约 9.1 MB）与压缩包（约 1 MB）主导，被复制进每个 web 构建的 `dist/`；`heartnano` 作为小体积回退存在，以防足迹将来成为问题。
- **版本漂移。** 运行时钉在 0.3.0；上游升级是带新哈希的重新引入，而不是依赖版本提升，资产清单测试是抓住未记录变更的守卫。
