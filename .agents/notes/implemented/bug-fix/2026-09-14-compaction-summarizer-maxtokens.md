# Agent Note: Raise compaction-basic's default summarization maxTokens

Status: implemented

English | [中文](2026-09-14-compaction-summarizer-maxtokens.zh.md)

## Problem

A live dsh session ("Deep diving," `~/dev/mattcarvercom`, routed to `vllm-3090`/`qwen3.8-27b`, 150k context) kept hitting `CONTEXT_WINDOW_EXCEEDED` for hours after the same-day retry-authorization fix ([[2026-09-14-overflow-recovery-retry-verification]]) was already live — that fix correctly stopped the session from looping forever on one unfixable overflow, but the user was still blocked: nearly every turn hit the overflow again shortly after starting.

Diagnosed from the same session's decompressed event log (`session.v3.jsonl.zstd`): most `compaction/start` → `compaction/end` pairs across the affected hours carried `error: "summarization truncated at the token cap (incomplete checkpoint)"` rather than landing a `compaction/summary`. That error comes from `packages/compaction/compaction-basic/src/summarizer.ts`'s `finishError()`, mapped from the auxiliary summarization call's `finish.kind === 'max-tokens'` — the model ran out of its own requested output budget mid-summary and never finished. `compactSurfaceRegion`'s transaction only commits a replacement after `summarizeCompaction` succeeds, so a truncated summarization call lands *nothing*: no reduction, no progress, and the very next request (or next turn) hits the identical oversized prompt again.

`compaction-basic`'s summarization call requests a fixed `maxTokens` (default `8192`, unconfigured in this deployment) regardless of how large the shadowed region is. The successful compactions in the same log shadowed consistently large regions (`shadowedTokenCount` 78132–101411 tokens) — condensing that much dense, code-and-detail-heavy agentic conversation into the package's required 8-section structured Markdown checkpoint (preserving "exact file paths, commands, error strings, identifiers, numeric values, function signatures") can legitimately need more than 8192 output tokens on its own. The package's own architecture note already named this class of risk directly: "provider output caps can be spent on hidden or surfaced reasoning tokens and summary size is unpredictable" — this deployment hit exactly that, repeatedly, against a fixed default that had no margin for either factor.

A parallel investigation traced the routed model's actual `enable_thinking` wire dispatch through `@earendil-works/pi-ai`'s `openai-completions` adapter (`resolveChatTemplateKwargValue`/the `qwen-chat-template` branch) to check whether hidden reasoning tokens specifically were the cause: with no `reasoningEffort` requested, both dispatch paths compute `enable_thinking: false` for this route, so reasoning is very likely *not* directly implicated for this specific model's config as configured. That leaves the summary's own necessary size as the primary, better-evidenced explanation — though the package's own documented uncertainty ("summary size is unpredictable") means either or both factors can recur on a different provider or model.

## Decision

Raised the built-in default in `packages/compaction/compaction-basic/src/config.ts`'s `resolveConfig()` from `maxTokens: 8192` to `maxTokens: 24576` (3x). This is a default only — `BasicCompactionConfig.maxTokens` and the per-route `modelPolicies[].maxTokens` override remain fully configurable, unchanged; deployments needing a different figure for a specific route already have the mechanism to set one.

24576 was chosen against the observed data, not picked arbitrarily: the largest observed shadowed regions in the diagnosing session were ~100k tokens, and `compaction-basic`'s pressure trigger only fires once total usage crosses `thresholdRatio × contextWindow` (default `0.8`, i.e. 120,000 tokens on a 150k-window route) — so the auxiliary summarization call's own request (replayed shadowed-region prefix + this maxTokens) stays comfortably under most routed models' own context window even at the new, larger cap, while giving real headroom for both a legitimately long structured checkpoint and any reasoning-token consumption on a model where that does turn out to be a factor.

## Alternatives considered

**Disable reasoning explicitly for the summarization call** (set an explicit `reasoningEffort` on its `GenerateOptions`). Not done: tracing `@earendil-works/pi-ai`'s actual dispatch showed that omitting `reasoningEffort` entirely already resolves to `enable_thinking: false` for this route's configuration (`options.reasoningEffort` is falsy either way, and `resolveChatTemplateKwargValue`'s `!!reasoningEffort` computes `false` in both the omitted and explicit-`'off'` cases) — so an explicit `'off'` would be a no-op here, not a fix, and compaction-basic has no provider-agnostic way to request "the lowest available effort" that would differ from omission without adding vendor-specific coupling the package deliberately avoids.

**Add a per-model override in this deployment's own cordis.yml/preset instead of changing the package default.** Considered, but this deployment's active preset (`~/.dsh/.agent-presets/standard-nosearch/agent.cordis.yml`) is a local, non-repo customization — a fix living only there would not reach anyone else running this fork, and would not appear in `git log`/PR review the way the user asked for. The package default was also observed as too low in an absolute sense (unrelated to this one route), matching the architecture note's own general warning about summary-size unpredictability — worth fixing at the source rather than papering over per-deployment.

**Make `compactIfNeeded`'s context-overflow branch retry with a larger `maxTokens` on a `max-tokens` truncation, similar to the pressure branch's `compactionRetries` loop.** A more invasive behavioral change (adds a second retry dimension, needs its own budget/backoff, touches the transaction's failure/retry semantics) for a problem a simple default increase already resolves for the actually-observed case sizes. Left for a future change if a fixed cap still proves insufficient after this increase.

## Consequences

Compactions condensing large, detail-dense spans (this rig's typical agentic-coding conversations) have roughly 3x the room to finish a complete checkpoint before hitting their own output cap, without needing any deployment-side configuration. A deployment whose routed model's context window is small enough that a 24576-token summarization call plus its replayed prefix could itself risk overflow should set a smaller `maxTokens` via `modelPolicies` for that route — the new default assumes routes in the 128k+ context class this rig and most current agentic-coding models use.

This does not fix every possible cause of `summarization truncated at the token cap`: an unusually large shadowed region, or a model that does spend real hidden reasoning tokens on this call despite the dispatch tracing above, can still truncate. `overflowRetries`/`maxOverflowRetries` and the retry-verification fix from earlier the same day remain the backstop that keeps a still-truncating compaction from looping instead of failing fast.

## Testing

Updated `packages/compaction/compaction-basic/tests/compaction-basic.spec.ts`'s `resolveConfig({})` default-shape assertion to `maxTokens: 24576`. No other test hardcoded the old default (the two tests calling out `maxTokens: 8192` explicitly pass it as an override, unaffected by the built-in default). Full `compaction-basic`/`agent-loop`/`llm-retry`/`agent` suites (201 tests), repo-wide `typecheck`, and `lint` pass.

**Also fixed as part of this branch**: the prior same-day fix's follow-up commit removed three `oxlint-disable-next-line typescript/no-unnecessary-condition` comments in `compaction-basic/src/index.ts` as apparently-unused, verified only via linting that one file standalone (`npx oxlint <file>`) — which lacks full cross-package TypeScript project type information and produced a false "unused" result. The repo's real gate (`pnpm run lint`, which builds the host face first for complete type info) still needs those three directives; a fresh clean full-project run on this branch caught the regression before merge. Restored them. **Lesson recorded for next time**: never trust a standalone single-file `oxlint` run to judge whether a type-aware directive is genuinely unused — only the full `pnpm run lint` (or an equivalent run with the complete project's built type information available) is authoritative for `typescript/*` rules.
