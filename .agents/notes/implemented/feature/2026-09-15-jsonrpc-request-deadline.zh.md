# Agent Note: JSON-RPC 行传输的每请求截止时间

Status: implemented

[English](2026-09-15-jsonrpc-request-deadline.md) | 中文

## 问题

`JsonRpcLineTransport.request` 限制一个请求的唯一机制是调用方提供的中止信号。没有信号时,针对沉默或对端已死的请求——接受了请求但从不响应,或一次永不完成的握手——会永远等待下去,因为传输层只在流出错、关闭或被关闭时才结算待处理请求,而卡住但还活着的流不满足其中任何一种。消费方不得不为每个请求自建计时器,并把失败映射进自己的错误词汇(`dsh-sdk` 客户端用客户端级 `RequestTimeoutError` 包裹它的传输);其余每一个 JSON-RPC 消费方——首当其冲的是子代理 runner——则完全没有截止时间,沉默的 codex 进程正是借此无限期挟持一次运行。

## 决定

`request` 接受一个选项对象:`request(method, params, options?)`,其中 `JsonRpcRequestOptions { signal?: AbortSignal; timeoutMs?: number }`,取代了这个 pre-stable API 上的位置信号——仓库内传信号的调用方(`dsh-sdk` 客户端与 codex app-server wire 的三处调用)现在传 `{ signal }`——而 `JsonRpcTransportPeer` 接口保持不变,因为该契约的服务端只调用 `notify`。

正的 `timeoutMs` 会装上一个截止时间;它触发时,传输层用与放弃相同的清理(一个 `release` 闭包取消截止定时器并摘除中止监听)移除待处理项,并以暴露 `method` 与 `timeoutMs` 的类型化错误 `JsonRpcTimeoutError` 拒绝,调用方无需解析消息即可区分截止时间与协议错误。截止之后到达的响应被丢弃——待处理表已经为空,因此不会为可能永远不会来的响应保留任何状态,也不存在需要清理的状态。`0` 或缺省的 `timeoutMs` 让请求保持无界,因此使用 harness 的 `0 = 关闭` 约定的已验证 `Config` 值可以直接透传。

## 考虑过的替代方案

**保留位置信号,追加第二个位置参数 `timeoutMs`。** 两个可选位置参数读起来像一个有序对,下一个每请求控制将不得不移动每个参数位置;选项对象把每请求控制归入一个有文档的表面之下。

**在每个消费方装截止时间,就像 `dsh-sdk` 客户端今天做的。** 每个消费方都会复制计时器加放弃加清理的簿记,并以消费方本地的错误类型失败;传输层拥有待处理项表,截止时间及其清理属于那里。SDK 客户端在此之上保留它更丰富的客户端级超时——消费方策略与传输机制组合而非竞争。

**扩展 `JsonRpcTransportPeer` 接口加入选项。** 没有任何消费方通过接口带选项调用 `request`——该契约的服务端只做 `notify`——扩展它就是没有消费方的公开变更。具体类承载扩展后的签名,并保持对未变接口的结构可赋值性。

**对非正的 `timeoutMs` 值抛错。** harness 的超时设置以 `0 = 关闭` 作为其关闭值约定;拒绝 `0` 会迫使每个未来的消费方在透传值之前先在设置词汇与传输词汇之间做转换。

## 后果

- 有界请求现在可以更快地以传输级类型化错误失败;卡住的对端不再能让待处理工作越过其截止时间。
- 具体类上的位置信号调用形态消失(pre-stable 线路库;仓库内调用方在本变更中已更新,release-candidate 线上的库外调用方需要一个一行的选项对象变更)。
- 截止时间在有界请求待处理期间保持事件循环存活,且每个结算路径都会清除它,因此已结算的请求不留下任何句柄;`0 = 无界` 的请求不装任何定时器。
- 线上格式不变:这是对既有请求/响应流的每请求控制,因此会话事件、会话格式版本与 Python SDK 镜像都不受影响。

## 测试

传输规格固定:截止触发时以 `JsonRpcTimeoutError` 拒绝(带 `method` 与 `timeoutMs` 字段和文档中的消息)并清空待处理表;截止后到达的响应被丢弃且不恢复状态;截止定时器在响应、放弃与传输关闭时被清除;`0` 不装截止;既有的放弃测试通过新的选项对象形态通过。`dsh-sdk` 客户端与 `dsh-server` 通道不变并通过。
